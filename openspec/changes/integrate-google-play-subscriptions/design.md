## Context

The app distributes through two channels: F-Droid (free, open-source) and Google Play (monetized via subscriptions). The codebase uses Android Gradle product flavors for this split. The gplay flavor currently differs from fdroid only in application ID and some packaging exclusions. Adding subscriptions requires Android-level billing library integration and Dart-level purchase flow — both must be gated behind the gplay flavor so the fdroid build is entirely unaffected.

The Flutter ecosystem provides the `in_app_purchase` package (first-party, Google-maintained) as the standard way to integrate Play Billing. However, adding it to `pubspec.yaml` means the native plugin code compiles into both flavors. We must ensure the fdroid flavor never initializes billing APIs and handles the absence of Google Play Services gracefully.

## Goals / Non-Goals

**Goals:**
- Integrate Google Play Billing for subscription products (monthly/yearly tiers)
- Freemium model on gplay: 1 sync profile free, unlimited profiles with active subscription
- Block creation of second profile and block enabling extra profiles for unsubscribed gplay users
- When subscription expires: pause (disable) all profiles beyond the first; restore previous enabled state on re-subscription
- Ensure fdroid flavor builds, runs, and has full feature access without any billing dependency at runtime
- Provide a subscription management UI (view plan, subscribe, restore purchases) and upsell bottom sheet
- Use compile-time flavor detection (`--dart-define`) to select the billing implementation

**Non-Goals:**
- Server-side receipt validation (MVP uses local validation via `in_app_purchase`)
- Cross-platform billing (iOS/Web — Android-only)
- Free trial or introductory pricing logic in the client (handled by Play Console configuration)
- Promo codes or offer redemption UI
- Subscription analytics or revenue tracking

## Decisions

### Decision 1: Dart interface abstraction over `in_app_purchase`

**Choice**: Define an abstract `SubscriptionService` class in `lib/subscriptions/` with two concrete implementations:
- `GplaySubscriptionService` — wraps `in_app_purchase` for product listing, purchasing, and entitlement checks
- `FdroidSubscriptionService` — returns hardcoded "entitled" for all checks, no-ops for purchase methods

**Rationale**: Keeps billing logic testable and swappable. The fdroid implementation never imports or touches `in_app_purchase`, so the plugin's native code is dormant at runtime.

**Alternatives considered**:
- *Conditional Dart imports (`dart.library.io`)* — can't gate on flavor, only on platform
- *Runtime plugin check* — `in_app_purchase` might crash on fdroid if it tries to bind to Play Services; riskier
- *Separate pubspec.yaml per flavor* — Flutter doesn't support per-flavor pubspecs; would need a monorepo or build script hack

### Decision 2: Flavor detection via `--dart-define`

**Choice**: Pass `--dart-define=SUBSCRIPTIONS_ENABLED=true` in `flutter build` commands for gplay flavor. The Dart code reads `bool.fromEnvironment('SUBSCRIPTIONS_ENABLED', defaultValue: false)` at startup and selects the appropriate `SubscriptionService`.

**Rationale**: Compile-time constant, zero runtime overhead, tree-shakes unused code. The fdroid build omits the flag entirely, defaulting to false.

**Alternatives considered**:
- *Runtime package-name check* (`PackageInfo.fromPlatform()`) — works but adds a dependency (`package_info_plus`) and has runtime cost
- *Flavor-specific main.dart entry points* — Flutter doesn't support this natively; would require Gradle-level source set hacking

### Decision 3: Android Billing dependency and permission are flavor-specific

**Choice**:
- `src/gplay/AndroidManifest.xml` declares `<uses-permission android:name="com.android.vending.BILLING"/>` — merged only for gplay
- `build.gradle.kts` adds `implementation("com.android.billingclient:billing:7.1.1")` inside the existing `androidComponents.onVariants` block for `gplay` flavor
- No `src/gplay/kotlin/` needed — all billing logic lives in Dart via `in_app_purchase`

**Rationale**: Keeps the BILLING permission and native billing dependency out of the fdroid APK entirely. The `in_app_purchase` Flutter plugin's native Java code is still present (it's auto-generated by Flutter's plugin system), but without the permission and Gradle dependency it won't initialize.

**Alternatives considered**:
- *Gradle product-flavor dependency block* — possible but the existing build uses `androidComponents.onVariants` pattern; keeping it consistent
- *Separate billing plugin written in Kotlin with MethodChannel* — overkill; `in_app_purchase` already does this

### Decision 4: Purchase verification — local only (MVP)

**Choice**: Use `in_app_purchase`'s `queryPastPurchases()` to check active subscriptions and `InAppPurchase.instance.purchaseStream` to listen for new purchases. No server-side verification.

**Rationale**: Simple, no backend infrastructure needed. Sufficient for MVP. The Play Store itself prevents tampering at the device level (signed purchases). Server-side verification can be added later without changing the Dart interface.

**Risk**: A rooted device could theoretically spoof purchases locally. Mitigation: Acceptable for MVP; add server-side verification in a future iteration if fraud becomes a concern.

### Decision 5: Freemium model — 1 profile free (fixed first), multi-profile requires subscription

**Choice**: The premium feature gated by subscription is **creating or enabling more than 1 sync profile**. The free tier allows exactly 1 profile — the first one in the ordered list (by name). Enforcement points:

1. **Create Profile FAB on DashboardScreen** — before navigating to ProfileConfigScreen, check `isSubscribed || profiles.length < 1`. If blocked, show the upsell bottom sheet.
2. **Enable toggle on DashboardScreen** — when user tries to toggle a profile ON, check `isSubscribed || profileIndex == 0`. Only the first profile (index 0) is free; any other profile requires a subscription. If blocked, show the upsell bottom sheet.
3. **ProfileConfigScreen** — when editing a non-first profile without subscription, disable the Sync enabled switch and force `enabled: false` on save. This prevents bypassing the dashboard enforcement by editing the profile directly.

Editing and deleting existing profiles is always free.

**Why fixed index instead of enabled count**: The previous model counted enabled profiles and allowed up to 1 at a time, but the user could disable profile A and enable profile B — effectively choosing which profile gets the free slot. The fixed-index model prevents this: only the first profile in the alphabetical list is free. If the subscription expires and the user has profiles A, B, C, only A can be enabled; B and C require a subscription. This is simpler to explain ("your first profile is free") and harder to game.

**Subscription expiration behavior**:
- When `isSubscribed` transitions from `true` to `false`, iterate all profiles and disable (`enabled = false`) all but the first one (index 0), keeping its enabled state unchanged.
- Before disabling, persist which profiles were previously enabled so they can be restored on re-subscription.
- When `isSubscribed` transitions from `false` to `true`, re-enable profiles that were active before expiration.

**Rationale**: Concrete, testable, and transparent to the user. The user gets a clear value proposition: "one sync pair is free, more requires a subscription." The fixed-index approach prevents the user from cycling the free slot across profiles. The auto-restore on re-subscription avoids frustrating users who had to manually re-enable multiple profiles.

### Decision 6: Upsell presentation

**Choice**: A bottom sheet dialog showing subscription plans with pricing (fetched from Play Billing) and a "Subscribe" button. Not an AlertDialog — the bottom sheet is less disruptive and can display richer content (plan comparison, pricing).

**Rationale**: Shows value immediately (prices, plan details) without a full-screen context switch. The user can dismiss it with a swipe and continue using their 1 free profile.

## Risks / Trade-offs

- **[Risk]** `in_app_purchase` plugin native code exists in fdroid APK but BILLING permission is absent → Plugin initialization may log warnings/errors at startup → **Mitigation**: `FdroidSubscriptionService` never calls `InAppPurchase.instance`, so the plugin is never initialized on fdroid. The plugin's Flutter registration is lazy.
- **[Risk]** Google Play Billing Library version must stay compatible with `in_app_purchase` plugin → **Mitigation**: Use the version bundled by the Flutter plugin; don't override it in Gradle unless necessary. Check compatibility in release notes.
- **[Risk]** Subscription state cached in memory may be stale if the user cancels externally → **Mitigation**: Refresh on app resume via `WidgetsBindingObserver.didChangeAppLifecycleState`; add a manual "Restore purchases" button.
- **[Risk]** Expiration auto-disable may conflict with background sync running while the app is in background → **Mitigation**: The expiration check runs on resume (foreground transition), not during background execution. Sync All only iterates enabled profiles, so disabled extras are never synced.
- **[Trade-off]** `--dart-define` flag requires build command changes and CI updates → Acceptable; already needed for gplay builds (the flavor flag itself is a build command difference).
